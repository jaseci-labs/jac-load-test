# jac loadtest — Command Reference

The load itself is generated by [Locust](https://locust.io): users, scheduling, workers, statistics,
the console tables and the HTML report are Locust's. This tool adds the HAR replay, correlation,
jac-scale auth, the body check, thresholds and the JSON report.

```
jac x loadtest <har_file> [options]
```

Settings resolve as **CLI flag → `jac.toml` (`[loadtest]`) → built-in default**.
The **toml** column marks flags that can be set in `jac.toml`; flags marked "CLI" are never read
from it (they change per run or are sensitive).

**Exit codes:** `0` all thresholds passed (or none set) · `1` a threshold failed · `2` config or
tool error (bad HAR, missing flag, auth failure). Failed thresholds print to stderr, for example
`THRESHOLD FAILED: p95 612.4ms > limit 500.0ms`.

## Load shape

| Flag | Default | toml | Description |
|---|---|---|---|
| `har_file` | required | CLI | `.har` file from Chrome DevTools or any recorder |
| `--url` | required (monolith) | CLI | Target base URL; replaces the recorded origin, path and query are kept |
| `--mode` | `monolith` | yes | `monolith` (all traffic to `--url`) or `microservice` (route by path prefix) |
| `--vus` | `1` | yes | Virtual users. Each one is a Locust user with its own HTTP client |
| `--workers` | CPU count | yes | `1` runs in this process; more starts a Locust master here and that many worker processes. User ids are unique across workers, so no two workers log in the same account |
| `--iterations` | `1` | yes | Full HAR replays per VU |
| `--duration` | — | yes | Hard wall-clock limit for the run; loops VUs until it elapses if `--iterations` is unset. Not with `--step-load` |
| `--ramp-up` | `0s` | yes | Stagger VU start over this time |
| `--step-load` | off | yes | Add `--step-vus` every `--step-duration` until a threshold breaks or `--step-max-vus`; reports the capacity knee. Works with `--workers`; needs `--step-vus` and a stop condition. Each step is judged on its own traffic window |
| `--step-vus`, `--step-duration`, `--step-max-vus` | `0`, `30s`, `0` | yes | Step-load parameters |
| `--think-time` | `none` | yes | `none` or `real` (the recorded wait between requests) |
| `--timeout` | `30s` | yes | Per-request timeout; exceeded requests are `TIMEOUT` errors |
| `--include-static` | off | yes | Replay images, fonts, CSS and JS too |
| `--csrf` | off | yes | Echo a `csrftoken`/`_csrf` cookie as `X-CSRFToken` on non-GET requests |
| `--health-check` | — | yes | Extra unauthenticated `GET` per VU per iteration; own report row, excluded from totals and the global gate |

## Data and identity

| Flag | Default | toml | Description |
|---|---|---|---|
| `--accounts` | — | yes | Per-VU pool: inline JSON map or array, or a `.json`/`.csv` path. One login per distinct account; VUs wrap round-robin. Use a file outside local runs (inline passwords land in shell history) |
| `--skip-failed-accounts` | off | yes | Continue when some accounts cannot authenticate: those users stop, the rest run. Without it the run aborts with exit 2 |
| `--register-path`, `--no-auto-register` | `/user/register`, on | yes | Create a missing account on login 401. `201` = created; `400 IDENTITY_TAKEN` / `USER_EXISTS` = wrong password, reported not retried |
| `--username`, `--password` | — | CLI | One shared account (a one-entry pool). `--accounts` wins if both are given |
| `--login-path` | `/user/login` | yes | Path identifying the login entry in the HAR (not replayed) |
| `--param` | — | CLI | `"Endpoint.body.title=titles.csv"`, repeatable. Feeds a `body.<path>`, `query.<name>` or `header.<name>` field from a file (one value per line, `file.csv:col`, or a JSON list); rows advance by `(vu_id, iteration)` |
| `--correlate` | auto | CLI | `"Producer.response.<path> -> Consumer.body.<path>"`, repeatable; wins over detection |
| `--no-auto-correlate` | off | yes | Replay bodies exactly as recorded |
| `--fail-on-correlation-miss` | off | yes | Exit 1 when a correlation rule never captured a value, or captured one but never injected it |

**Tokens** work in bodies, queries, headers and URL paths: `{{uuid}}`, `{{vu_id}}`, `{{iter}}`,
`{{randint:a,b}}`, `{{now}}` / `{{now+30s}}` (`s`/`m`/`h`), `{{account.<col>}}`,
`{{env.<VAR>}}`. Unknown tokens are left as written, and a `--param` naming a field the body lacks
does nothing. A parameterized run is usually slower than an unparameterized one, because identical
payloads were hitting a warm cache.

**Correlation** is automatic: the HAR is scanned at startup for server-generated ids that a later
request reuses, and each VU threads its own. The rules in force print to stderr when the run
starts. If a value appears in more than one recorded response (a create call, then a list query that
returns the same id), it is threaded from the earliest one, the response the client saw first, and
the choice is printed and listed under `correlation.notes` in the JSON report; pass `--correlate`
to use a different source. A value that was never
captured fails the consumer as `CORRELATION_MISS`.

Every run reports what each rule did (producer runs, captures, injections, misses) in the JSON
report's `correlation` section. A rule whose producer answered but never yielded the value is
named in a warning on stderr, and so is one that captured a value but never injected it (its target
path is not in the consumer request). Either skips every request that depends on it, the first
almost always because the response envelope or schema changed. `--fail-on-correlation-miss` makes that a non-zero exit.
`--correlate` source paths under `data.result.reports.` and `data.reports.` work on both jac-scale
response envelopes.

**Re-auth:** a mid-run `401` triggers one re-login for that user and one retry; a second `401` is `AUTH_EXPIRED`. A recorded `401` is left alone.

## Correctness checks

| Flag | Default | toml | Description |
|---|---|---|---|
| `--assert-json` | — | CLI | `PATH=VALUE`, repeatable: a JSON response field must equal a value (`*` = present). Scope to one endpoint with `ENDPOINT:PATH=VALUE`. Only checked when the status already matched |
| `--no-body-check` | check on | yes | Turn off `APP_ERROR_IN_200` (an `error`/`errors` key, inner `status >= 400`, `reports[].success: false`, or empty `reports` where the recording had results, inside `data` / `data.result`). A bare `{"ok": false}` is not flagged; use `--assert-json 'ok=true'` |
| `--check-shape`, `--fail-on-shape-drift` | off | yes | Flag (or fail on) responses missing top-level keys the recording had |
| `--poll-until` | — | CLI | `ENDPOINT:PATH=VALUE[,VALUE...]`, repeatable. For 2+ adjacent recorded calls to one endpoint, keep re-sending the block's request until `PATH` reaches a value, then score the block as one result with the real wait as its latency. One rule per endpoint |
| `--poll-error-until` | — | CLI | Same syntax; a terminal failure value (`POLL_TERMINAL_ERROR`) |
| `--poll-timeout`, `--poll-interval` | `60s`, recorded gap | yes | Limit for a whole poll block (timeout: `POLL_TIMEOUT`) and delay between polls |
| `--infra-block-threshold` | `3` | yes | Distinct endpoints returning an identical non-JSON body in one 10 s window before it is classed `INFRA_BLOCK_SUSPECTED` (excluded from the error rate). Below 2 disables |

## Thresholds

| Flag | Default | toml | Description |
|---|---|---|---|
| `--fail-on-error-rate` | — | yes | Exit 1 if the error rate exceeds N percent |
| `--fail-on-p95`, `--fail-on-p99` | — | bare form | Exit 1 above N ms. Bare number = global; `ENDPOINT:MS` = that endpoint only (repeatable, CLI) |
| `--abort-on-fail` | off | yes | Stop as soon as a threshold is breached; partial report |
| `--threshold-start-delay` | `0s` | yes | Skip threshold checks for this long (metrics still collected) |

## Output

| Flag | Default | toml | Description |
|---|---|---|---|
| `--report-format` | `console` | yes | `console` (Locust's tables), `json` (our report) or `html` (Locust's report; needs `--report-out`) |
| `--report-out` | — | CLI | Write json/html to a file |
| `--debug` | off | CLI | One stderr line per request |
| `--services-map` | — | CLI | Microservice mode: `'{"svc": "http://host:port"}'`, bypasses the service apps declared in `jac.toml` |

Microservice mode needs direct network access to service ports, so it works locally or inside a
cluster, not against a remote production deployment.

## WebSocket and GraphQL

No flag needed: connections and GraphQL traffic in the HAR are detected and replayed with the HTTP
entries, and replayed in order inside each user's iteration and reported as `WS /path [connect]`, `WS /path` (one row per frame) and `GraphQL /path` rows. GraphQL over HTTP replays like any
HTTP entry; subscriptions use `graphql-ws`. WebSocket frames are only present in HARs from
recorders that keep them (Playwright `recordHar` with `mode: "full"`, mitmproxy); a plain Chrome
export has none, so the connection is opened and reported as a `[connect]` row with a one-time
warning.

## jac.toml example

```toml
[loadtest]
vus = 20
workers = 4
ramp_up = "10s"
timeout = "30s"
mode = "monolith"
think_time = "none"
fail_on_error_rate = 1.0   # percent
fail_on_p95 = 500          # ms
fail_on_p99 = 1000         # ms
threshold_start_delay = "30s"
report_format = "console"
```

## Examples

```bash
# 50 VUs, 10 s ramp-up, 100 iterations each
jac x loadtest recording.har --url http://localhost:8000 --vus 50 --iterations 100 --ramp-up 10s

# 20 distinct accounts, realistic pacing
jac x loadtest recording.har --url http://localhost:8000 --vus 20 --accounts accounts.csv --think-time real

# CI gate: fail on p95 > 500 ms or errors > 1%, stop early
jac x loadtest recording.har --url http://staging:8000 --vus 20 --iterations 100 \
  --fail-on-p95 500 --fail-on-error-rate 1 --threshold-start-delay 10s --abort-on-fail

# Wait for a recorded polling loop to finish, scored on the job's real outcome
jac x loadtest launch.har --url http://localhost:8000 \
  --poll-until 'job_control:data.state=running' --poll-timeout 300s

# HTML report
jac x loadtest recording.har --url http://localhost:8000 --report-format html --report-out results.html
```
